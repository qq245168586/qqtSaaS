# Embedding 与 MongoDB 语义检索优化技术方案

版本：设计稿 v1.0  
日期：2026-10-18（北京时间）  
适用项目：天美意趣趣特管理工具第二期，Electron 桌面 / NestJS API / MySQL  
状态：方案与预算评估；未安装 MongoDB、未下载模型、未调用收费模型、未变更生产配置或业务代码。

## 1. 建议与决策

建议增加一层可关闭、可重建的语义检索服务：

**MySQL 保留业务主库；MongoDB 保存检索投影、向量和检索缓存；embedding 负责查找相似材料与历史习惯；现有对话模型负责理解原文并生成草稿；规则和 MySQL 最终决定字段是否有效；用户确认后才写入单据。**

本轮不建议迁移订单、送货单、排班或财务统计到 MongoDB。先优化 BOM 材料候选及公司/执行人/送货署名建议，再评估跨历史订单搜索。MongoDB 故障时，App 继续走现有 MySQL、名称匹配与规则链路。

模型部署有三个可独立切换的选择：

| 方案                   | embedding                                   | 订单/BOM/排班理解           | 建议                                                        |
| ---------------------- | ------------------------------------------- | --------------------------- | ----------------------------------------------------------- |
| A：线上 API            | 百炼 text-embedding-v4                      | 现有 DeepSeek API           | 优先建立效果和成本基线，改造少、无本地推理运维              |
| B：本地 CPU + 线上理解 | 本地 BGE-small 中文向量模型                 | 现有 DeepSeek API           | 有本地化要求时的推荐折中方案                                |
| C：完整本地 CPU 推理   | 本地 BGE-small；可比较 Qwen3-Embedding-0.6B | 本地 Qwen3-4B GGUF 量化模型 | 作为离线/数据不外发的独立验收路线，不能默认与线上大模型等效 |

这里“本地”默认指企业控制的服务器或局域网主机，而不是每台员工电脑。ECS 上自托管也是自托管推理，但数据仍离开员工电脑；只有部署在企业内网并禁用外部回退，才是企业内网不外发。每台 App 独立携带模型会增加安装体积、索引同步和设备差异，不作为首期方案。

**现阶段推荐先用 A 做评测，保留 B 的部署接口；不为了节省极低的 embedding 调用费，先采购一台只做向量化的服务器。若明确要求材料与历史语料不发送给 embedding 厂商，直接选 B。** B 仍会把本次解析原文及获准检索上下文发送给对话模型，不能称为完整本地化。

## 2. 当前实现与实际切入点

本方案依据当前仓库源码核对，未假定服务器已装 MongoDB，也未重新核实生产 CPU、内存或当前业务数量。

| 模块         | 当前源码                                          | 当前机制                                                              | 本轮优化位置                                       |
| ------------ | ------------------------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------- |
| 业务数据库   | `server/src/db.ts`                                | TypeORM + MySQL，迁移管理，不自动同步表结构                           | 保留；增加 outbox 与检索状态表                     |
| 全局 AI      | `server/src/external.ts`、`ai-assistant.ts`       | retail / delivery / schedule 草稿、原文依据、Zod 校验                 | 注入分模块检索结果，不给模型直接写库权限           |
| 公司带出     | `company-learning.ts`                             | 主营关键词、近180天人工纠正；至少3条、占比至少70%的稳定记录优先于默认 | 不改变现有优先级，增加关键词未覆盖时的相似语义参考 |
| 执行人       | `assignee-learning.ts`                            | 全局部门、按业务日期过滤员工、历史关键词投票                          | 只在有效候选中增加相似订单历史信号                 |
| 送货署名     | `delivery-personnel.ts`                           | 公司内按客户、商品和次数加权；四种署名各自排序                        | 检索历史送货情景，仍按字段分别带出                 |
| 渠道         | `order-channels.ts`                               | 微信、小程序、小红书、大众点评 + 保存历史频率                         | 继续使用频率，不必强行向量化                       |
| BOM          | `bom.ts`                                          | 读取所选公司有效金蝶商品；别名规则 + 名称包含/字符重叠 + 规格单位分数 | 先精确/别名，再语义召回，再规格单位验证            |
| BOM 自动带出 | `bom.ts`                                          | 当前第一名分数≥90、领先第二名≥15时预选                                | 保留旧分数含义；新语义分数不能直接套用旧阈值       |
| 送货商品历史 | `delivery-catalog.ts`、独立 `products` / 送货明细 | 自由输入，历史带出                                                    | 与 `kingdee_products` 永久隔离                     |

这里的旧 BOM 分数是业务启发式分数，不是概率。当前源码的 BOM 别名查询与候选汇总也应统一复核目标商品是否停用、软删、公司不符；加入向量检索时不能继承无效别名候选。

## 3. 优化目标与不适用范围

### 3.1 应当解决的问题

1. 配方写“淡奶油”，库里商品带品牌、完整包装规格时，能找出更合适的候选。
2. “杯子蛋糕”“纸杯蛋糕”等不同表达，能参考已确认的相似业务习惯。
3. 复制同类客户订单时，给出公司、部门、执行人、制单/仓管/业务/送货人员的合理建议与依据。
4. 减少把全部商品或全部历史记录塞进提示词，降低上下文长度和无关干扰。
5. 商品更新、员工离职、单据删除后，相应建议失效或刷新。

### 3.2 不应交给向量模型处理

- 金额、数量、税额、汇总、客户对账与打印状态：继续查 MySQL，使用既有十进制计算。
- 时间、日期、人员资格、加班/调休与例休结转：继续使用确定性规则。
- BOM 克/千克、个/箱等换算：必须有明确换算依据，语义相似不能制造换算系数。
- 鸡蛋规则：沿用已确认的整蛋折算和默认50g政策，不由检索改写。
- “无糖/含糖”“全脂/脱脂”“动物/植物奶油”等差异：保留为结构化限制或冲突，不用相似度自动替代。
- 送货单商品：用户可以完全自由输入；找不到历史也不阻止保存，不映射金蝶商品。
- 自动创建/删除单据、自动覆盖排班、后台代替用户确认：不在范围内。

Embedding 是相似度表示，不是订单解析模型，也不是把用户的习惯直接训练进大模型。所谓“学习”主要是保存可追踪的人工选择，再用于检索和排序；首期不做微调。

## 4. 总体架构

```text
Electron / H5（保留现有认证与表单）
    │ HTTPS，业务请求
NestJS API
    ├─ 认证、模块边界、规则、输入校验、最终权限
    ├─ 理解模型适配器 ── DeepSeek API 或内网 llama-server
    ├─ 检索协调器
    │    ├─ MySQL：精确名称、别名、业务习惯、权威资料
    │    ├─ Embedding 适配器：线上 API 或内网 CPU 服务
    │    └─ MongoDB：分域检索投影 + 向量搜索
    └─ 用户确认后的 MySQL 业务事务
             ├─ 正常业务表 / 原审计表
             └─ retrieval_outbox + retrieval_source_state
                          │ 异步消费、重试、幂等
                  独立索引 Worker
                          ├─ 生成去敏投影与向量
                          └─ 更新 MongoDB 检索集合
```

App 不直连 MongoDB，不持有数据库密码或 embedding Key。推理服务不接触 MySQL，也不直接保存单据。MongoDB 返回候选 ID 后，API 必须重新从 MySQL 取有效记录，检查版本、业务日期和访问范围。

选择 NestJS 原生服务 + 官方 MongoDB Node 驱动即可，不引入 LangChain、Mongoose、Kafka、Redis 或 Kubernetes 作为首期强制依赖。后续确有吞吐瓶颈再增加相应组件。

## 5. 模型选型：CPU 本地与 API

### 5.1 Embedding 候选

| 模型                      | 部署方式                | 向量维度                   | 适用性与代价                                                                    | 首期定位              |
| ------------------------- | ----------------------- | -------------------------- | ------------------------------------------------------------------------------- | --------------------- |
| BAAI/bge-small-zh-v1.5    | CPU，ONNX/INT8          | 512                        | 中文短材料名与短订单场景，模型卡列出512 token序列长度；不能假定英文商品效果同等 | 本地 CPU 首选评测基线 |
| Qwen/Qwen3-Embedding-0.6B | CPU，需验证具体推理后端 | 最大1024，可配置更低维     | 支持多语言与长文本，但参数更多，CPU批量索引和并发资源需求更大                   | 中英混合召回评测备选  |
| 百炼 text-embedding-v4    | HTTPS API               | 推荐1024；官方提供多档维度 | 无本地模型维护，中文及多语言；有按 token 费用及数据外发边界                     | API 首选评测基线      |

模型能力与维度依据：[BGE 模型卡](https://huggingface.co/BAAI/bge-small-zh-v1.5)、[Qwen embedding 模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)、[百炼同步 embedding API](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)。

选择模型时，用本系统的“品牌 + 名称 + 规格 + 单位”与真实别名测试，不能直接用通用榜单决定采购。API选1024维只是初始配置；BGE的512维属于另一向量空间，不能与API的1024维混用。即使 Qwen 与 API 都返回1024维，也不能交叉检索。

### 5.2 订单/BOM/排班理解模型

- 线上：保留当前 DeepSeek 兼容接口和 `deepseek-flash` 模型入口，先不引入第二家理解模型。模型别名对应版本可能改变；记录响应模型标识和配置修订号，用固定样例检查回归。
- 本地：选官方 `Qwen/Qwen3-4B-GGUF` 的 `Q4_K_M` 作为 CPU 原型基线，通过 llama.cpp 的 `llama-server` 提供兼容接口；不是承诺4B能达到现有线上模型的解析效果。
- 输出使用非思考模式、JSON结构约束、有限输出长度；本地后端的 JSON Schema 能力必须单独验证，不能仅因接口“兼容”就假定支持同一参数。
- 先对比3类任务和BOM完整配方的正确率，再决定是否切换。相似度检索变好，不代表本地理解模型就不会把订单拆错、漏日期或漏材料。

官方依据：[DeepSeek 当前模型与价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)、[Qwen3-4B 官方 GGUF](https://huggingface.co/Qwen/Qwen3-4B-GGUF)、[llama.cpp server](https://github.com/ggml-org/llama.cpp/tree/master/tools/server)。选这些作为可复现基线，不表示它们是所有场景下的最新或最强模型。

### 5.3 是否要重排模型

第一期先使用结构化规则、历史投票与排序融合，不部署额外 reranker。若 Top20 已有正确材料但 Top1经常错误，再比较 Qwen3-Reranker-0.6B 或独立重排API。CPU重排限制候选数量与并发，不能为20种材料各对100个候选逐个跑模型。

## 6. CPU 本地化部署、配置与模型缓存

### 6.1 服务位置

首选单独的企业内网推理服务或隔离ECS进程，保持员工 App 轻量。Windows/Mac客户端统一调用现有API；数据库与推理服务不对公网开放。

如果放在办公室电脑上，需要承担电脑休眠、关机、局域网访问和固定服务地址问题；不建议让办公室电脑的临时IP成为云API的唯一推理依赖。可通过受控私网链路访问，不把模型端口裸露公网。

### 6.2 轻量 embedding 的具体技术路线

新增独立 TypeScript 推理进程：`@huggingface/transformers` + 其 Node CPU 后端。使用经过验收的 BGE ONNX 制品；官方原模型与社区ONNX转换物要分别记录来源、许可证与文件哈希。转换来源可评估 [onnx-community 制品](https://huggingface.co/onnx-community/bge-small-zh-v1.5-ONNX)，不把社区量化文件当作原作者质量保证。

配置原则：

- 模型部署时下载一次，写入 `/var/lib/tmy-models/bge-small-zh-v1.5/<revision>/`；启动只读本地目录。
- 固定模型 revision、ONNX文件SHA256、tokenizer、量化方式、pooling与归一化版本。
- BGE按模型卡采用匹配的CLS池化及归一化，并固定query侧指令；文档侧使用各自模板。不能直接拿默认mean pooling替代而不测效果。
- 运行时 `env.localModelPath` 指向模型目录，`env.allowRemoteModels=false`；下载失败、文件缺失或校验不符时进程健康检查失败，不偷偷联网补下载。
- CPU初始2个推理线程、1路请求；批处理从4条开始；BGE业务文本先控制在256 token以内，整体不超过模型512 token限制（计入特殊token和query指令）；先预热再接流量。线程/批大小必须经CPU配额与负载验证。
- 单条材料名通常很短；长订单按业务子块切分。模型最大长度之外的内容不得静默截断成“完整理解”。

Transformers.js 本地模型加载能力见[官方配置文档](https://huggingface.co/docs/transformers.js/en/custom_usage)。配置字段最终按锁定依赖版本核验。

可设计一个内网 `/embeddings` 服务，输入 `{texts,purpose}`，输出 `{vectors,profile_id}`；有明确条数、字节数、超时限制。NestJS适配器负责转换各家协议，App无需理解模型协议。

### 6.3 本地理解模型的原型启动配置

以下是待验收的运维命令示例，不是本次已运行命令；参数应按固定 llama.cpp 构建版本复核：

```bash
llama-server \
  --model /var/lib/tmy-models/qwen3-4b/Qwen3-4B-Q4_K_M.gguf \
  --host 127.0.0.1 --port 8092 \
  --n-gpu-layers 0 --threads 4 \
  --ctx-size 4096 --parallel 1
```

固定本地业务模型别名，适配器转换到实际服务的model名称。Qwen3的思考开关由聊天模板或受支持的参数关闭；不要向所有供应商硬塞同一参数。4096上下文和单路并发是试验起点，不是模型上限；过长BOM应提示分批或改用明确启用的API方案，不能无声截断。

每个服务使用独立systemd用户、资源限额、健康检查和启动顺序；模型保持常驻，不能每次点击解析都重新加载。推理CPU池与MongoDB/MySQL争用时，优先降低离线索引Worker速度，保住业务查询。

### 6.4 硬件资源规划起点

下表为待实测的资源预留，不是厂商最低要求、实测吞吐或采购报价；CPU型号、内存带宽、量化及上下文会明显改变结果。

| 服务                       | 原型资源预留                                      | 生产注意点                                                                     |
| -------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------ |
| BGE-small CPU embedding    | 2–4 vCPU、2–4GB RAM，模型目录预留2GB              | 单路起步，离线回填限速；INT8效果需对照原模型                                   |
| Qwen3-Embedding-0.6B CPU   | 4–8 vCPU、4–8GB RAM，磁盘预留5GB                  | 短文本也需测P95；不要因支持长上下文就输入整库                                  |
| Qwen3-4B Q4 本地理解       | 8 vCPU起、独立16GB RAM预留，模型/运行空间预留10GB | 4B Q4权重理论量级约2GB，但实际文件、KV cache和运行内存更多；长上下文需更多内存 |
| MongoDB + mongot检索试验机 | 独立8 vCPU、32GB RAM、100GB SSD作为压测起点       | 多进程及副本集资源另算；不能把该行视为高可用配置                               |

已存在32GB以上的内网机器时可做隔离原型。若所有服务都放同机，不可把每行资源同时超售；需要按进程合计，尤其避免与生产MySQL共享内存。MongoDB高可用应另做跨主机副本与搜索节点设计，三个进程放一台机器不等于高可用。

本次未读取当前ECS硬件利用率，因此无法声称原服务器足以承载这些进程。

## 7. MongoDB 版本、向量搜索与部署选择

### 7.1 不能只安装普通 MongoDB

MongoDB向量搜索是搜索组件提供的能力；应用连接 `mongod`，自托管需要配套 `mongot` 维护搜索索引。普通集合索引 `createIndex` 不是向量搜索索引，存入一个数字数组也不会自动具备ANN检索能力。[MongoDB 自托管搜索说明](https://www.mongodb.com/docs/search/self-managed/current/)

截至本次查阅，官方当前兼容页列出的组合涉及 MongoDB Server 8.3 / mongot 1.70.1及以后；具体要求依部署方式与兼容矩阵判断。不要套用旧文章中的“任意MongoDB 8.0/8.2即可”方案。现有运维文档记录的服务器是Alibaba Cloud Linux 4，不能直接假定等同于官方列出的RHEL或其他受支持平台。[兼容矩阵](https://www.mongodb.com/docs/search/self-managed/current/deployment/compatibility-requirements/)

`mongodb-atlas-local`只用于开发/CI，官方不把它列为生产目标。本地Windows/Mac可用Linux容器验证，生产自托管则选择正式支持的平台、版本、replica set与搜索进程拓扑。MongoDB change streams依赖副本集或分片部署，不以standalone代替。参考[副本集与change streams](https://www.mongodb.com/docs/manual/replication/)。

### 7.2 本项目选择顺序

1. 隔离环境做兼容验证：固定镜像/二进制版本与digest，确认CPU指令集、Linux发行版、磁盘和备份方式。
2. 自托管试点：单独受支持的Linux主机/容器宿主，业务API通过内网访问；检索可故障回退。开发单节点不包装为高可用。
3. 正式高可用：按官方拓扑建设多主机副本与搜索节点，评估资源和费用后决定。
4. MongoDB Atlas是另一个可选运维方案，但涉及地域、网络、数据托管和独立费用，不默认替用户采购，也不默认数据迁出既定环境。

如果自托管兼容、资源或支持条件不满足，先保持原SQL规则而非勉强上线向量链路；必要时仅保留Mongo文档投影试验。不要临时改成每次把全部向量拉回App计算距离。

## 8. 数据边界与集合设计

### 8.1 分域集合

建议使用独立数据库 `tmy_retrieval`，按业务分集合，模型空间再版本化：

| 逻辑集合                      | 数据来源                                  | 关键边界                                        |
| ----------------------------- | ----------------------------------------- | ----------------------------------------------- |
| `bom_materials_<profile>`     | MySQL `kingdee_products` + 已确认材料别名 | 必须按所选公司、启用状态过滤                    |
| `retail_examples_<profile>`   | 已保存零售任务及人工纠正                  | 当前共享工作台可跨公司参考；仍检查真实访问权限  |
| `delivery_examples_<profile>` | 送货历史明细及有效署名                    | 仅送货历史；不含金蝶BOM商品；署名习惯按单据公司 |
| `schedule_examples_<profile>` | 结构化排班表达模板及受控确认样例          | 优先模板，不默认存员工姓名和个人历史            |
| `embedding_cache_<profile>`   | 去敏文本哈希与向量                        | 无原始电话/地址；过期可重建                     |
| `retrieval_traces`            | 请求级候选ID、策略、耗时、错误            | 不存Key、完整原文或完整向量；短期保留           |

公司、部门、员工的“管理属性”与“单据归属”不同：部门和员工没有公司属性。不能为便利索引新增员工所属公司。公司字段仅用于单据投影和BOM商品账套；API根据具体任务构建过滤器，不把所有检索机械地按公司隔离，也不机械地全局共享。

### 8.2 投影结构（设计类型）

```typescript
import type { Long } from "mongodb";

type RetrievalDomain = "bom" | "retail" | "delivery" | "schedule";
interface RetrievalProjection {
  _id: string; // domain:source_type:source_id，全部ID字符串
  domain: RetrievalDomain;
  workspace_id: string; // 当前固定共享工作台；不等同于company_id
  source_type: string;
  source_id: string;
  source_revision: Long; // BSON Int64，同一源单调递增，控制并发/删除
  owner_company_code?: "tri" | "tmy";
  visibility: "shared" | "restricted";
  allowed_employee_ids?: string[];
  search_text: string; // 服务器模板生成的去敏检索文本
  normalized_name?: string;
  spec_attributes?: Record<string, string>;
  product_unit?: string;
  is_active: boolean;
  is_deleted: boolean;
  embedding_profile: string;
  embedding: number[]; // 适配器校验维度、有限值、非零向量
  source_hash: string;
  indexed_at: Date;
  projection_schema_version: number;
}
```

业务原文、价格、电话号码、图片不需要完整复制到MongoDB。候选名称仅供检索展示；最终表单字段回读MySQL。投影不是新账本，不能拿其金额做对账。

### 8.3 Embedding 文本模板

BOM：`材料名称=安佳淡奶油；已确认别名=稀奶油；规格=1L；单位=盒；类别=乳制品`。

零售习惯：`商品=纸杯蛋糕/布丁；业务=门店配送；客户类型=食堂；人工确认公司=趣趣特；部门=蛋糕部`。可检索上下文保留匿名化客户键；向外部模型发送时不包含电话与精确地址。

送货：`业务=送货单；商品=自由新品面条；客户键=customer_x；归属=天美意`；署名目标用源记录ID在服务器回读。

排班：`表达=某员工日期范围内9点上班；类型=工作；开始=09:00；正常跨度=9小时`。检索只帮助理解表达，不推导真实员工的休假余额或复制他人排班。

模板、分块、pooling、指令、量化方式都纳入 `embedding_profile`，例如 `bge-small-zh-v15-q8-cls-512-tpl1`。不同profile独立集合/索引，不在查询时混用。

## 9. MySQL 到 MongoDB 的可靠同步

### 9.1 使用事务 Outbox，不做同步双写

业务保存事务中同时写业务表与Outbox；MongoDB写入由Worker异步完成。不能先写MySQL再写MongoDB并把“两者都成功”作为开单成功条件；也不能先更新MongoDB后MySQL失败留下虚假记忆。

拟增两张MySQL表：

| 表                       | 主要字段与约束                                                                                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `retrieval_source_state` | `source_type,source_id`唯一；`source_revision BIGINT`、`is_deleted`、`projection_hash`、`updated_at`；用于所有源表统一版本及删除墓碑                        |
| `retrieval_outbox`       | `event_id`主键；源类型/ID/修订号/操作；`status`、`attempts`、`available_at`、`lease_until`、`lease_token`、错误码；唯一源+修订号；索引`status,available_at` |

MySQL BIGINT 在Node与API协议中用十进制string；Mongo投影使用驱动的BSON Long做修订号比较，通过Long.fromString等受校验转换，不转成JavaScript number，也不按字符串字典序比较。候选响应中的source_revision再转换为十进制string。

### 9.2 Worker 正确性

1. 用短事务领取到期事件和租约，支持 `FOR UPDATE SKIP LOCKED`；外部embedding请求不占用数据库锁。
2. 读取当前源状态及权威记录，生成确定性投影；多个同源事件可以合并到最新版本。
3. 查询embedding缓存；未命中才调用模型。
4. 调用返回后再次检查源修订号；过期结果丢弃/重排，不写回旧内容。
5. Mongo原子更新只接受更高修订号；同修订号必须内容哈希一致。唯一 `_id` 冲突不能通过重试成无条件覆盖。
6. 删除先写高版本墓碑及 `is_deleted=true`，避免较慢的旧向量任务把删除记录重新激活；检索过滤墓碑，且最终SQL再检查删除状态。
7. 仅持有有效lease_token的Worker可以把Outbox标记完成；崩溃后租约超时可重领。
8. 至少一次投递 + 幂等结果，不宣称跨MySQL/Mongo“恰好一次”。

不能简单按自增event_id保存全局消费游标：不同事务提交顺序可能与ID顺序不同，跳过尚未提交的小ID会丢事件。首期直接领取pending任务，清理done任务用独立保留期。

### 9.3 回填、导入和补偿

- 开启事件记录后分页回填现有有效资料，用当前修订号覆盖，在线修改通过版本保护，不停机清空历史。
- 金蝶Excel导入按商品变更发事件；相同哈希不重新embedding。同步导致BOM别名或待匹配项变化，也触发相应源的更新。
- 单据修改/删除、员工离职、别名禁用必须有事件。批量导入分批提交/生成事件，不能一次在请求内向量化全库。
- 对源记录做日常哈希对账，补偿历史脚本、手动修库或漏埋点；删除也要检查，不只扫描活跃记录。
- 初始目标：常规变更60秒内可检索；超限告警。权威SQL有效性检查保证即使索引延迟，也不把已删除商品或离职员工带入最终表单。候选修订号落后于MySQL时，丢弃或基于最新资料重新检索/排序，不沿用旧规格和旧习惯。

## 10. 查询链路与排序

### 10.1 单次全局 AI 请求

1. 验证现有会话、原文长度、指定模块；按用户选择或轻量路由判断模块，不依赖向量相似度单独决定要创建哪类单据。
2. 先做显式日期/公司/姓名识别；用户明确指定优先。
3. 按模块检索少量已确认样例；无可靠样例时保留原有提示词，不强行拼接。
4. 理解模型输出带原文依据的结构化草稿；Zod与当前模块边界验证。
5. 候选目录、公司习惯、执行人、署名建议按字段补全；重新读MySQL和员工资格。
6. 展示现有填写页，用户手动确认创建；保存成功后才产生可追踪反馈。

模型不得从相似历史复制日期、数量、价格、客户地址或真实姓名来补缺。原文无日期仍要求补填；有日期无小时的任务仍默认09:00；历史排班日期仍允许补录。

### 10.2 BOM 材料流程

先解析配方与原始材料行，再对去重后的每种材料并行限速查询：

```text
当前账套 + 明确编码
    → 有效人工锁定别名
    → 已确认精确别名 / 完整名称与规格
    → 名称检索 Top20 + 语义检索 Top20
    → 合并去重 + 规格/类别/单位约束
    → 规则与历史重排，输出Top5
    → 稳定明确匹配可预选；仅语义命中先作为建议
    → 未匹配项一次性批量弹窗
    → 用户确认，沿用现有BOM保存/金蝶导出
```

不将每行材料交给LLM做一次“自由选商品”；LLM不生成商品ID，API只接受本次有效候选中的ID。所有缺失材料集中处理，保留“需在金蝶新增商品”的现有流程。

### 10.3 优先级与习惯更新

公司建议：原文明确公司/用户当前选择 → 现有稳定人工纠正 → 主营默认 → 语义历史辅助 → 不确定提示。首期语义不能直接压过已命中的主营默认；评测稳定后，才讨论有足够人工证据时是否升级。

BOM建议：有效人工锁定别名 → 精确名称/规格 → 明确确认历史 → 语义候选。锁定指当前BOM别名能力，不假装现有公司建议已经有管理员锁定配置。

员工：先按日期、部门/业务验证可用集合，再在集合中排序；员工本身不分公司。送货署名仍支持自由文字，同名真实员工存在时按业务日期检查资格。

反馈按“来源单据 + 字段 + 上下文”唯一记一票。重复打开、重复保存同样内容、重复点击候选不新增票；修改覆盖旧票，删除撤销对应票。区分 `explicit_changed`、`explicit_confirmed`、`auto_prefill` 与 `imported`，自动带出后直接保存不能当成一次强人工纠正，否则会自我强化错误。

建议保留当前180天习惯窗口做基线；语义邻居只在同类上下文形成投票，不把所有相似文本混成全局最高频。初始稳定条件沿用/参照3个独立已确认来源、70%一致率；这是待校准业务门槛，不是模型置信度。

### 10.4 混合检索

精确规则独立于排序融合。对于需要融合的候选，可采用RRF：

`RRF(d) = Σ 1 / (60 + rank_i(d))`

随后加结构化规格兼容和已确认习惯特征。RRF、Mongo向量相似度和旧BOM分数不是同一量纲；不得把0.88相似度展示为“88%一定正确”。对用户展示“名称一致 / 人工历史 / 相似语义”等依据，而非伪概率。

可选reranker仅处理通过硬限制的少量候选；绝不把“植物奶油与动物奶油用途类似”解释为可自动替换。

## 11. 向量索引与查询示例

以下针对通过兼容验收、支持对应API的 MongoDB Vector Search；`PROFILE`、集合及服务器范围均由服务端映射，不接受App提交原始Mongo查询。

索引定义示例（API向量profile，1024维）：

```json
{
  "name": "bom_vec_api1024_v1",
  "type": "vectorSearch",
  "definition": {
    "fields": [
      {
        "type": "vector",
        "path": "embedding",
        "numDimensions": 1024,
        "similarity": "cosine"
      },
      { "type": "filter", "path": "workspace_id" },
      { "type": "filter", "path": "owner_company_code" },
      { "type": "filter", "path": "embedding_profile" },
      { "type": "filter", "path": "is_active" },
      { "type": "filter", "path": "is_deleted" }
    ]
  }
}
```

通过官方Node驱动支持的 `createSearchIndex` / `createSearchIndexes` 创建，等待索引就绪后才接业务；这与普通唯一索引不同。另为来源ID、名称与更新时间建普通索引。[Node驱动索引文档](https://www.mongodb.com/docs/drivers/node/current/indexes/)

查询示例（TypeScript片段，`queryVector`为校验过的真实1024维向量）：

```typescript
const pipeline = [
  {
    $vectorSearch: {
      index: "bom_vec_api1024_v1",
      path: "embedding",
      queryVector,
      numCandidates: 400,
      limit: 20,
      filter: {
        workspace_id: workspaceId,
        owner_company_code: selectedCompany,
        embedding_profile: activeProfile,
        is_active: true,
        is_deleted: false,
      },
    },
  },
  {
    $project: {
      _id: 1,
      source_id: 1,
      source_revision: 1,
      score: { $meta: "vectorSearchScore" },
    },
  },
];
```

这里使用 `$vectorSearch` stage，不混用 `$search` 中另一个 `vectorSearch` operator的语法。该stage位于管道开头，过滤字段须作为filter索引；Top20 / numCandidates400是可调起点，不是性能承诺。Mongo官方建议ANN起始候选数可取limit约20倍，再以数据评测调节。[查询与过滤规则](https://www.mongodb.com/docs/atlas/atlas-vector-search/vector-search-stage/?deployment-type=self&embedding=auto&interface=driver&language=java-sync)

私有模式下，零售等涉及人员访问范围的集合必须增加相应filter字段并在查询前限定，不能先从全库Top20取出再只靠前端隐藏。共享模式的workspace过滤也由服务器注入；单据公司过滤是否使用由业务用途决定。

## 13. 缓存、超时、降级与索引迁移

### 13.1 缓存

- 向量缓存键：`hash(profile + purpose + canonical_text)`；query/document用途不同不得误复用。
- 用户电话、地址先去除，再生成文本和哈希；不要以“只有向量”推断绝无敏感信息泄露风险。
- 同文本并发请求使用single-flight；多进程允许少量重复调用，靠唯一键幂等，不引入复杂分布式锁。
- 可设查询向量缓存7天；这是策略不是保证只调用一次，过期、内容或模型版本变化会重算。与已要求的图片缓存是两套机制，图片下载策略保持不变。
- 候选结果缓存30–60秒；返回前仍做MySQL有效性和权限检查。删除或停用事件主动失效。
- TTL仅清理非权威缓存和短期trace，不能TTL删除人工规则、业务单据或删除墓碑而让旧任务复活。

### 13.2 延迟与回退

初始目标：命中缓存的检索增量P95≤300ms；未命中embedding链路预算约2秒。它们是压测目标，不是本次实测。

调用层为embedding、Mongo查询、理解模型分别设deadline与熔断；不要把查询阶段800ms误用为包含冷启动和embedding的总时限。在线请求不做长重试，后台Worker指数退避加随机抖动，达到次数进死信并告警。

Mongo/embedding不可用：走现有SQL规则，返回“智能建议暂不可用，仍可正常填写”；不把整个App切成“当前离线”。理解模型不可用：保留原文和手工入口。C方案禁外发时不得自动偷偷回退DeepSeek；只有显式配置允许才可调用外部。

### 13.3 换模型

创建新profile和新集合 → 回填 → 完整性对账与效果评测 → shadow比对 → 原子切换配置 → 保留旧集合可回退 → 观察稳定后按清理计划删除旧索引。迁移期磁盘容量至少考虑双份向量/搜索索引，不只考虑单份原始向量。

任何模型、tokenizer、量化或模板变更都可能改变相似度分布；不能沿用旧阈值直接上线。

## 14. 安全与数据治理

- 当前MySQL认证、公开工作台/网页密码和私有账号模式继续有效；由服务器生成候选范围。
- Mongo只绑定loopback或内网，分只读API用户、写入Worker与运维管理员；不同主机通信使用受控内网与TLS，不开放27017或模型端口到公网。
- 来源文本和历史样例是数据，可能包含提示注入。通过固定JSON容器注入上下文，声明其不具备规则或工具权限；最终schema、目录与原文验证必须在模型外执行。
- 价格、地址、员工姓名尽量不进入embedding语料；确需发送给外部理解模型的内容按业务需要与用户授权范围控制。之前一次测试授权不自动覆盖所有历史数据批量上传。
- 模型下载固定版本和哈希，原模型、ONNX量化制品、llama.cpp及Mongo组件分别核对许可证和分发义务，不将模型随安装器分发给所有用户。
- 不记录Key、token、数据库URI、完整复制群聊或完整向量到通用日志。
- 不增加OSS桶、RAM角色或对象存储依赖。使用现有ECS磁盘/备份约束；备份应考虑独立故障域，同机另一目录不能防整盘/整机丢失。

## 15. 预算：线上 API 与本地 CPU 对比

### 15.1 价格口径和边界

以下模型单价于2026-10-18查阅官方页面；币种人民币，不假设免费额度、缓存优惠或促销。ECS费用随地域、实例族、购买方式、磁盘与带宽变化，本次没有进入账号控制台取得正式报价。

- 百炼 text-embedding-v4北京地域：官方页面所列同步输入价格为 **0.0005元/千token，即0.5元/百万token**，支持所列多档维度；示例按此计算。[官方API与价格](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)
- DeepSeek Flash：按当前官方**高峰、缓存未命中输入2元/百万token、输出8元/百万token**做保守计算；当前空闲时段相应减半，缓存命中另有单价。[官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)
- 实际收费token与汉字不是1:1。记录厂商usage，按实际调用地域和账单复核。
- CPU自托管没有逐token厂商调用费，但有机器、电力、磁盘、维护和备用资源成本；不能写成“免费”。

### 15.2 embedding 示例

假设初次索引10,000条去敏短文，每条平均120token：

`10,000 × 120 / 1,000,000 × 0.5 = 0.60元/次全量初始化`

月查询3,000次，每次180token；增量更新1,000条，每条120token：

`(3,000 × 180 + 1,000 × 120) / 1,000,000 × 0.5 = 0.33元/月`

这是示例负载，不是当前数据库实测。若一次BOM解析有20种不同材料，向量查询次数应按材料去重后的条数计，不按“一次点击=一次embedding”计算。失败重试、模型切换重建、缓存命中率也要记录。

### 15.3 理解模型示例（按高峰未命中，不计优惠）

| 月解析次数 | 每次输入 / 输出token假设 | 输入费用 | 输出费用 | 合计        |
| ---------- | ------------------------ | -------- | -------- | ----------- |
| 500        | 2,000 / 600              | 2.00元   | 2.40元   | 4.40元/月   |
| 3,000      | 3,000 / 800              | 18.00元  | 19.20元  | 37.20元/月  |
| 10,000     | 5,000 / 1,000            | 100.00元 | 80.00元  | 180.00元/月 |

不把“输出JSON只有800token”当成所有调用事实：长BOM、重试、额外路由及思考输出都会增加消耗。首先关闭不必要的思考与反复重试，实际按usage重新估算。检索上下文如果拼接过多，反而增加输入费；不能承诺加embedding必然省钱。

### 15.4 部署和总账示例

以下是**做预算用的占位价格，不是阿里云报价，也不是保证能买到指定规格的价格**：设共同Mongo检索基础设施实际月成本为 `M`，独立CPU embedding主机/资源为 `E`，本地理解模型主机/资源为 `L`，备份/磁盘/网络增量为 `S`。

| 方案                           | 月成本公式，采用上面的3,000次中档例子 | 纯核算演示：M=500、E=150、L=500、S=50元/月 |
| ------------------------------ | ------------------------------------- | ------------------------------------------ |
| A 线上embedding + 线上理解     | M + S + 0.33 + 37.20                  | 587.53元/月                                |
| B 本地CPU embedding + 线上理解 | M + S + E + 37.20                     | 737.20元/月                                |
| C 本地CPU embedding + 本地理解 | M + S + E + L                         | 1,200.00元/月                              |

同机部署时，不能把同一台机器重复计入M、E、L，应使用实际升级/扩容增量。模型调用费用不是Mongo部署费用；使用API也仍需要共同的检索基础设施。已有可用内网主机时E或L的新增采购可为0，但仍计电力、维护和机会成本。

建议为初期自托管检索环境先预留 **500–1,500元/月的基础设施评估额度**，再用实际支持的拓扑和ECS控制台报价替换；这不是高可用承诺。全CPU理解路线另预留机器资源和评测成本，不靠上述占位值直接下单。正式多机高可用、额外备份主机和运维人力另列，可能显著高于试点额度。[ECS计费因素](https://help.aliyun.com/en/ecs/billing-overview)

若新购内网机器，暂以16–32GB以上内存、SSD、可常开CPU主机为选型目标；具体产品/采购价本次未询价，不虚构一笔一次性硬件报价。现有服务器能否复用，要先采集负载再决定。

### 15.5 成本临界点

在同样Mongo成本下，单独为省embedding费购买每月150元资源，按0.5元/百万token计，需要约 **3亿embedding token/月**才抵消这150元，尚未计运维。这说明本项目本地embedding主要价值是数据控制、稳定性或复用现有算力。

中档理解请求每次示例成本为0.0124元。若本地理解额外资源500元/月，约40,323次同等token请求/月才能在纯调用费上抵消；还必须同时满足正确率、延迟与运维成本。此比较仅为参数化算账，不表示CPU机器真能承载这些请求。

建议配置月预算告警，例如50%/80%/100%；超预算停止新后台全量embedding，保留业务与人工入口。不得为了省几元API费牺牲开单或排班可用性。

### 15.6 开发与维护工作量

初步拆分：现状采样与脱敏评测2–3人日；Outbox/投影/重建4–6人日；混合检索和业务接入4–6人日；CPU适配与模型制品管理2–4人日；联调、安全、故障回退与灰度3–5人日。完整本地理解另增加约3–6人日的模板、性能与质量验收。

以上是范围估算，不是交付承诺；按实际人日单价计算一次性开发预算，并给基础工作量留约20%不确定性。部署Mongo的兼容/资源问题、历史数据清洗或高可用建设需要单列。

## 16. 效果、性能与CPU验收

### 16.1 固定样例集

至少准备200条经授权、脱敏且人工标注的材料/订单案例，并按时间/客户分训练参考与保留测试集，避免同一历史订单既参与记忆又参与评测。保留完全未确认的“新材料”负样本。

必须覆盖：

- 焦糖布丁、布丁烧、纸杯蛋糕、意面和方包的公司与部门；人工多次纠正后的变化。
- 同客户同交付多商品只产生一张零售任务，金额不从历史复制。
- 金蝶材料品牌/规格近似、同名不同规格、停用商品、未知材料，及两公司相同名称不同编码。
- 送货自由商品在金蝶不存在也可保存；BOM候选绝不进入送货商品历史。
- 员工无公司、按业务日期离职校验；历史排班可补录；未知姓名不猜人。
- 无日期必须补填、有日期无小时09:00；数量单位正确；鸡蛋沿用50g默认规则。
- 删除后旧任务晚到、重建时在线修改、重复保存不增加强反馈、私有会话不泄露其他员工数据。

### 16.2 需要记录的指标

| 类别     | 指标                                                                 |
| -------- | -------------------------------------------------------------------- |
| 召回     | BOM Recall@5 / @20、正确候选是否出现、跨公司串库率                   |
| 带出质量 | Top1正确率、人工修改率、误预选率、未知材料错误匹配率                 |
| 理解     | 模块正确率、订单合并、字段完整率、日期/数量/单位准确率、schema通过率 |
| 同步     | Outbox最老积压、重试与死信、源版本与索引版本差异、删除可见延迟       |
| 资源     | CPU、RSS、内存带宽影响、峰值磁盘、冷热模型延迟、每类请求P50/P95      |
| 成本     | 请求次数、输入/输出usage、embedding命中率、索引全量/增量花费         |

验收目标：权限/公司边界违规为0；离职资格与确定性计算回归全部通过；保留测试集的人工修改率不劣于现有方案，并争取相对下降20%；语义候选提升以统计结果判断，不预先承诺100%匹配。仅语义召回第一期不直接自动选中高风险BOM材料。

### 16.3 CPU 专项压测

对BGE q8、Qwen embedding、Qwen4B理解分别测：冷启动、预热后单条、batch4、并发1/2/4；长文本按64/256/512 token和实际长BOM分档。记录机器型号、物理核/vCPU、线程、量化、模型revision、运行时版本。

CPU本地理解给出“首token时间”和“完整JSON完成时间”；不能只看tokens/s。单路较快但同时3人使用可能排队，需压测队列等待。上线门槛可初设短订单P95≤15秒、完整BOM≤30秒；如果达不到，保持API或手工入口，不宣称CPU足以替代。

压测不得与生产MySQL抢满CPU；不以猜测的每秒多少条当作采购保证。

## 17. 分阶段实施与回滚

| 阶段            | 工作内容                                                           | 进入下一阶段条件                   |
| --------------- | ------------------------------------------------------------------ | ---------------------------------- |
| P0 评测准备     | 统计有效源数、采样长度、确认数据外发范围；取得实际ECS/内网资源报价 | 有基线、授权边界和明确预算         |
| P1 隔离原型     | Mongo兼容拓扑、A/B embedding、BOM候选检索；不接生产保存            | 正确率与延迟数据可复现             |
| P2 可靠同步     | 增量迁移、Outbox、Worker、删除墓碑、回填与对账                     | 崩溃重试/乱序/删除测试通过         |
| P3 影子模式     | 同一请求后台计算新候选，不改变用户当前默认                         | 保留集和真实分布下不越权、不劣化   |
| P4 辅助候选     | 先BOM建议，再公司/员工/署名；低信心批量确认                        | 人工修改率下降，成本与故障可控     |
| P5 可选本地理解 | C方案独立对比、单路CPU灰度                                         | 完整字段、日期、合并、吞吐达到基线 |

发布顺序：先兼容的服务器与迁移，开关保持off → Worker与回填 → shadow → 新App候选依据展示 → 小范围assist。不是必须把所有模型与App一起发一个大包。

回滚优先关闭 `RETRIEVAL_ENABLED` 或改mode=off，业务恢复原SQL建议；保留业务主库、Outbox和人工反馈。必要时停止Worker和切回旧profile。不能通过恢复整份旧业务数据库来回滚检索功能，也不能删除已确认单据。

## 18. 部署前最终检查

1. 当前ECS CPU、RAM、磁盘、架构与运行负载是否有余量；Alibaba Cloud Linux与目标Mongo组件是否在支持范围。
2. 选择A/B/C；若使用本地推理，确认是云上自托管、办公室内网还是每台客户端，不能把三者成本混算。
3. 获取实际Mongo拓扑、CPU主机、磁盘、备份和带宽报价；决定是否需要高可用。
4. 锁定模型与运行时版本、文件哈希、profile；BGE512与API1024分别建索引。
5. 明确允许发送的历史数据范围；默认先脱敏，不批量上传客户联系方式与员工资料。
6. 确认现有精确规则、人工习惯、金蝶/送货隔离及最终人工确认不会改变。
7. 完成兼容、故障回退、质量、同步与安全测试，再申请实施/生产切换；本文本身不触发安装、调用或采购。

## 19. 本次推荐结论

对当前业务，最有价值的是“规则 + 人工确认习惯 + 分域语义召回”，而不是换掉MySQL或把全部AI搬到员工电脑。

先以线上embedding + 现有线上理解模型建立可用基线，重点上线BOM候选和习惯召回。若需要语料向量化不外发，采用本地BGE CPU；保留线上理解时明确仍存在相应外发。完整CPU本地理解可以做，但作为独立路线验收，不为了几元调用费先承担机器与运维成本。

费用与性能均按实际usage、实际报价与固定样例结果复核；方案未包含任何已经实施或已经采购的声明。
