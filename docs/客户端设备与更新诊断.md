# 客户端设备与更新诊断

2026-11-24。适用于本次改动之后打包的客户端；已安装的 2.1.32/2.1.33 不能远程获得此能力。本次随 2.1.34 发布；2.1.32 用户按最新要求先手动安装 2.1.34。

## 请求标识

Electron 主进程统一封装业务 HTTP 请求、认证、附件和在线检查；更新器也携带相同设备与版本信息。

- `User-Agent: TMY-TRI-Manager/<version> (<platform>; <arch>) Device/<uuid>`
- `X-App-Version`、`X-Device-ID`、`X-Client-Platform`、`X-Client-Arch`
- `X-Request-ID`：每次业务请求独立 UUID；更新器每次检查刷新，请求与服务端响应可关联。

UUID 存在 Electron userData 的 `client-device-id`，普通升级保持不变。它代表安装配置，不采集主机名、MAC 地址或硬件序列号，不是认证凭据；清除配置或使用不同系统账户会得到不同编号。磁盘不可写时退化为当次运行编号，不阻塞业务。开发运行版本追加 `-dev`。

## 采集与上传

采集启动、HTTP/网络错误、IPC 错误、未捕获渲染异常、渲染进程退出、主进程未捕获异常，以及更新阶段。只记录固定事件代码、版本、HTTP 方法/状态、路径模板、请求编号、错误类型和去掉目录的 JS 文件/行列。没有请求正文、响应正文、查询参数、令牌、用户名、客户资料或原始异常文本；因此需要结合请求编号排查，不能恢复完整原始异常。

本地 `client-diagnostics.json` 最多 200 条，同类事件 10 秒去重；每次最多上传 30 条。安装版取得会话后尝试上传，之后每分钟重试。仅删除服务端确认收到的事件；失败留待下次，不递归记录上传错误。开发运行不上传事件，但请求仍带诊断头。

`POST /api/client-diagnostics/events` 使用既有 JWT 鉴权、严格字段校验，64KB 请求上限、30 条/批、每 IP 60 次/分钟。服务端待写队列上限 100。不要通过此接口上传原始日志文件。

## 更新结果

点击“重启更新”前保存 `update-pending.json`（原版本、目标版本、尝试编号）。PowerShell 助手写 `update-helper-result.json`，记录就绪、等待 App 退出、启动安装器、安装结束/失败及退出码；等待原进程最多 120 秒。

下次启动读取回执：实际运行版本达到目标版本才记录 `update_succeeded`，否则 `update_incomplete`，即使安装器返回 0 也不能认定升级成功。成功后清理回执；未成功保留以便继续诊断。更新弹窗显示设备编号、当前版本及上次未完成提示。

这不意味着已确认或修复某台旧版 Windows 电脑的根因。macOS 上的单元测试和 Electron 冒烟测试无法代替 Windows 安装器端到端验证；旧版需取得原安装助手日志或安装新诊断版本后再次观察。

## 服务端存储与排查

默认目录为服务工作目录下 `var/client-diagnostics`，可用 `CLIENT_DIAGNOSTICS_DIR` 覆盖。目录 0700、文件 0600，属于服务账户，未增加公开查询日志接口。

- `devices.json`：最多 1000 个设备，记录当前版本、系统架构、最近访问时间；同设备同版本每分钟最多刷新一次。
- `events-YYYY-MM-DD.jsonl`：UTC 按日存储，单日最多 10MiB，滚动保留 30 天；新请求写入时每日清理。短期重传在服务进程内去重；重启后同事件 ID 可能重传，分析时应按设备和事件 ID 去重。
- 文件中的外层版本是上传时版本，`event.app_version` 是事件发生时版本；升级前暂存的错误不会被误归为新版错误。

运维使用受控服务器终端，根据弹窗的设备编号查 `devices.json` 和事件文件，再按 `request_id` 关联请求。不得将完整诊断目录开放到 nginx 静态路径。无需新增数据库表、付费服务或更改业务数据。

## 2.1.32 → 2.1.33 实包核对（2026-11-24）

已核对 `fead759` → `790ed5c` 的源码差异，并解开本地留存的两个实际 NSIS EXE：

- 安装器配置、自定义 NSIS、Electron 主进程、预加载、更新管理/启动助手源码没有变化；package-lock 仅顶层版本号变化，没有更新依赖。
- 两份 app.asar 共对比 16,374 个文件，变化仅为前端编译资源、入口 HTML 和 package.json 版本；包括 dist-electron 和 node_modules 的其余文件一致。
- 外层各 76 个文件，差异仅为 app.asar 与应用 EXE。EXE 的 .text、.rdata、.data 等代码/数据段一致，只有 .rsrc 资源段改变；两版 app-update.yml、elevate.exe 和 DLL 一致。
- 线上 2.1.32 SHA-256：`f9bdff48f6e3030abf8a1d6379c7175b787f00443e82a828162d9a4d8e47b42c`。
- 线上 2.1.33 SHA-256：`2baa1f26ad21efc071bd961803e377cda1bd7934abfa0ab8d7304e833d9fc066`。
- 上述值与本地发布包一致；公网 2.1.33 返回 200、长度 113091548；latest.yml 指向 2.1.33。

现有更新是 NSIS 整包安装，即使只变前端 JS/CSS，也需要安装程序静默替换应用包，并非单独热替换 TS/JS。差分下载和安装阶段是两个不同步骤。

旧版不足：更新入口使用自定义 PowerShell 助手等待退出后启动 `/S --updated --force-run`，没有调用 electron-updater 的标准安装执行器。标准 NsisUpdater 中的提权启动/启动失败兜底没有被这条自定义链路复用；这只是风险点，尚不能证明用户设备恰好遇到该情况。NSIS 自定义宏部分静默取消分支使用默认取消后 Quit；旧客户端仅检查安装退出码，不核对最终版本，所以安装中止时缺少明确反馈。

受影响电脑仍需实机日志才能确定具体阻塞点。2.1.32 自带助手失败时尝试写入 `%LOCALAPPDATA%\tmy-tri-manager-updater\pending\<实际缓存安装包文件名>.launch.log`；没有该文件并不证明安装成功。当前 Mac 无法实测 Windows 权限、杀毒、文件占用或卸载流程，不将包校验通过等同于 Windows 升级成功。

诊断接口已部署现有生产 API；线上合成诊断事件验证通过（0.0.0-test），验证了鉴权、字段拒绝、请求编号关联和私有目录落盘，没有写业务数据。客户端 105 项、服务端 116 项单元测试通过；独立 Electron 诊断冒烟通过。旧 public-smoke 在旧订单样例等待处超时，未将其报告为通过。上述核查时尚未发布安装包；随后用户授权发布 2.1.34，发布状态见 desktop/RELEASE-2.1.34.md。

2.1.34 安装助手改用 Process.WaitForExit，只等待安装程序本身，以免 Start-Process -Wait 等待包括新 App 在内的整个进程树而延迟写回执。依据：[Microsoft Start-Process 文档](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process?view=powershell-5.1)。失败原因未确认时仅显示最后记录阶段，不能凭阶段推定权限或文件占用。
