# 员工管理与排班技术设计

日期：2026-10-12 更新。业务口径见《员工管理与排班-需求文档》。技术栈沿用现有 TypeScript strict / NestJS / TypeORM / MySQL / Electron / React / Ant Design / RxJS，不引入第二套服务或独立员工数据库。

## 1. 分层

服务器 `employee-policy.ts` 集中管理上海业务日期、员工按日期的资格、真实日期验证；任务保存、AI执行人建议、送货署名建议和送货保存复用。`employee-schedules.ts` 提供排班查询与事务写入，纯函数用于标准结束、分钟统计与测试。前端 `Schedules.tsx` 提供月历和日编辑；共享月份、部门过滤和服务器快照进入原有 RxJS Subject→scan(reducer)→shareReplay 状态流。编辑表单和弹窗使用组件本地状态，所有最终结果重新从服务器读取。

## 2. 数据模型

### employees 增量

`left_on DATE NULL`：active通常为空；left必须有生效日期。`status` 保持active/left，未来离职亦为left，但可用性以left_on判定。已离职不提供复职或日期覆写，以免单个日期丢失多段履历。历史left且无日期的记录以既有updated_at日期回填并在交接注明；当前生产检查现有5人均active，无此回填影响。

### employee_schedules

`id BIGINT`，`employee_id BIGINT`，`work_date DATE`，`shift_kind work/rest/comp_leave`，`start_time CHAR(5)`（休息/调休可null），`overtime_minutes INT`，`timeoff_minutes INT`，`note VARCHAR(500)`，`version INT`，`created_by/updated_by BIGINT`，`created_at/updated_at DATETIME`，`deleted_at DATETIME NULL`。唯一 `(employee_id,work_date)`，另建(work_date,employee_id)索引。清除为软删除且递增version，重新建立沿用同一行并递增，保证陈旧请求不能绕过并发检查。无公司列。

### employee_schedule_audit

`id`、`schedule_id`、`employee_id`、`work_date`、`action save/clear`、`before_json LONGTEXT NULL`、`after_json LONGTEXT NULL`、`actor_id`、`created_at`。前后JSON仅存排班字段，无会话、密码或token。每次成功写入追加一行，与排班事务共同提交。无手动累计表，没有「直接更新余额」入口。

TypeORM增量迁移在原schema.sql同步定义表和字段，幂等检测列/表。仅新增结构、不会重建/删除现有业务表。服务器迁移前全库备份；迁移down拒绝自动删除新业务数据。

## 3. API

统一 `/api` 与现有JWT入口、Envelope。所有ID字符串，时间date/datetime字符串，分钟整数。

- `GET /employee-schedules?month=YYYY-MM&department_id=ID`：返回 `{today,month,days,employees,items,balances}`。employees附部门名、状态和left_on；items是月份内有效排班；balances每员工返回期初、已发生加班/调休、截至月末/今天余额、未来计划净值。响应不分页，单月最大31日×现有人员；查询限定日期、部门。其他员工目录继续既有分页接口。
- `PUT /employee-schedules/:employeeId/:date`：`{shift_kind,start_time,overtime_minutes,timeoff_minutes,note,version}`；首次version=0，已有/清除后的版本必须等于当前值。返回保存的行。校验真实日期、员工资格与分钟范围。休息不填调休，调休必须>0且不加班。工作默认08:00。带未知字段拒绝。
- `DELETE /employee-schedules/:employeeId/:date`：body `{version}`，任意有效日期均可清除；软删除，返回null。不允许把请求日期转为UTC后误判。
- `POST /employees/:id/departure`：body `{left_on:'YYYY-MM-DD'}`。锁员工记录，已有离职记录拒绝；保存status=left与left_on。不删除历史单据/排班；未来排班保留并提示处理。
- 员工原POST/PUT扩展 `left_on`；statusleft无日期的旧App离职操作以服务器当天为默认，以兼容未更新App。已离职记录只允许维护姓名/电话/相同部门，禁止用PUT复职或改离职日期。
- `POST /assignee-suggestions` 可附 `document_date`，旧客户端不附按上海当天；AI按解析的交付日期传入。任务最终保存仍独立校验。
- 送货人员建议可附 `delivery_date`，旧请求用当天。按员工姓名过滤失效候选，同时保持用户自定义署名；送货保存检查对应真实员工姓名的资格。重名存在有效员工时允许。

HTTP400非法值/无效日期/离职资格，404缺失员工，409版本冲突，401/403沿用认证授权；UI展示中文错误，冲突后重新加载排班。

## 4. 事务和一致性

1. 写入只校验真实日期，不以today限制历史日期；统计仍使用上海today划分已发生和未来计划。
2. 锁员工行，验证未删除与离职日期；锁对应排班行。所有写入都先锁同一员工，因此不存在「首次行尚不存在」并发插入窗口。
3. 读取当前version（不存在=0），不匹配则409。
4. 更新/插入（包括恢复软删行），version+1；追加审计。捕获异常回滚。
5. 查询在数据库事务同一快照内读取员工、月排班、汇总；按整数分钟计算，未来另算。清除离职后未来计划允许，保存离职后工作禁止。
6. 员工删除有任务或排班时拒绝；部门下有排班员工禁止级联软删，避免资料接口绕过保留规则。

所有累计由排班明细求和，无需月末任务，不存在重复结转。日期范围以(员工ID,日期)和日期索引覆盖；未来规模增大再引入只读月汇总缓存，不存第二套可修改的余额。

## 5. 前端

一级增加员工管理，员工资料从设置迁出；二级员工资料/排班管理。保留原有导航习惯配置，旧的员工页偏好归入新模块。员工编辑显示离职日期，列表提供单独离职弹窗；隐藏删除员工动作。

月历固定员工姓名列，31日横向滚动；每格显示开始/正常结束、休息/调休和时长；所有日期点击编辑。底部独立余额表说明已发生/计划口径，负余额高亮。数字小时用1/60粒度转换为整数分钟，显示使用小时+分钟，最终由服务器验证。编辑使用接口返回version；失败保留用户输入，不用本地乐观假保存。

业务选人监听单据日期，日期变更时移除不合资格选择；历史单据打开时可带出离职前员工。网页仅同步资格辅助与日期参数，不新增排班页面。

## 6. 验证与发布

纯函数测试覆盖合法日期/闰年、标准9小时和跨午夜、离职前/当天/未来、分钟级正负累计、跨月、未来不入账。隔离SQLite适配测试真实controller事务覆盖首次/更新/软删恢复、version冲突、历史PUT/DELETE成功和重算余额、审计、离職和删除保护，不修改生产真实员工或单据。

执行服务器和桌面strict typecheck/build/unit tests，并在隔离Electron测试员工资料/排班入口、日编辑和历史排班新增、修改、清除。服务器使用Workbench指定实例i-bp1gy4to0n4dh5gk7tuw，发布前备份DB和dist，上传新dist/迁移，执行迁移再重启tmy-api.service；检查health、排班只读API及原任务/送货接口。新App仅本地npm start，不生成版本更新manifest/安装包。

回滚：旧dist可运行带新增列的数据库；停止新增排班写入，恢复旧dist服务。不要down删新表或恢复整个旧库覆盖上线后的真实单据。需保留排班时运维全库备份。旧公司备份不支持新全局排班，公司恢复接口始终保留全局员工/部门，不覆盖排班；后续全局备份方案另做。
